# RUN-01 / RUN-02：证据驱动的可验证恢复方案（已采用）

日期：2026-10-29。用户已明确采用本方案，RUN-01/RUN-02实现与故障验证见[技术文档12](../../technical/12.任务停止与可验证会话恢复.md)。下文保留设计阶段的动机与验证计划；交付行为和限制以技术文档为准。

## 1. 推荐的项目亮点

**将“恢复聊天记录”升级为“恢复可核验的审计工作状态”：Pi恢复对话，Harness验证证据和执行边界，SQLite决定哪些结果已经正式提交。**

用户重启后可以知道：分析的是哪份源码、恢复到哪个安全边界、哪些证据被复用、哪些操作需要重做、是否可能产生额外模型用量。这个亮点建立在现有固定快照、逐步取证、受控工具、结果事务和独立人工复核之上。

这里的创新定位是本项目的审计恢复机制和可解释交互；不把采用SQLite、JSONL或普通会话保存本身作为原创技术。无需首版引入LevelDB、Redis/ZSet或修改Pi内部实现。

## 2. 需求与当前实现

RUN-01要求：主动停止、确认停止、不可取消的请求明确等待、保留任务与已完成结果。RUN-02要求：风险点边界恢复、已提交不重复、未提交可重跑并说明用量、原快照/配置、验证Pi原生会话能力、会话关联落SQLite、SSE补发与执行恢复分离。

当前代码的限制：

- pi-session-factory.ts显式使用SessionManager.inMemory，没有跨进程会话正文。
- agent-loop.ts的round/requests/calls、read集合、fingerprints、noProgress、evidenceBytes在局部内存。
- PathAnalysisService的evidence同样在当前执行栈；验证结果依赖实际读取材料，聊天中声称“已读过”不能替代它。
- 现有停止主要用于服务关闭/超时，不是完整的用户任务控制协议。
- SSE已有持久化及按游标补发，只说明事件可再看，不说明Agent在后台继续。
- 已有领取/结果事务与attempt校验可扩展为恢复后的提交保护，但目前不是完整检查点协议。

## 3. 已核查的Pi原生能力与尚待验证的部分

核查本地精确依赖@earendil-works/pi-coding-agent 1.2.0和[官方SDK文档](https://pi.dev/docs/latest/sdk)、[会话格式说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/session-format.md)。Pi提供持久SessionManager、按文件打开、树形entry/parentId、分支和上下文重建；官方明确SessionManager负责已完成上下文，不能仅修改agent.state.messages假装替换持久会话。

本地离线存储探针（.local/run-recovery-probe-QU1Jqa/result.json）只调用SessionManager，不初始化模型、不执行工具，结果为：

| 检查 | 观察 |
| --- | --- |
| 新建文件会话、追加、重新打开 | sessionId与leafId相同 |
| user/assistant/toolResult/assistant | 角色顺序恢复 |
| appendCustomEntry保存宿主状态 | 重开后可读，但不会自动进入模型上下文 |
| 只有toolCall、没有toolResult时重开 | 未完成调用仍在上下文，没有凭空出现工具结果 |
| 较早entry | 可以按ID取得，供后续安全分支试验 |

这证明原生存储可以作为基础；**尚不证明createAgentSession重新打开后一定正确续跑，也不证明中断工具、供应商协议和突然掉电边界已通过**。这些是实施前必须完成的DESIGN-02集成验证。探针记录是手工合成的无害消息，不是模型审计证据。

## 4. 核心结构：两个检查点层次

### 4.1 任务层：已经正式提交的路径边界

以pathId及其路径/规则/快照身份为执行单元；只有通过原文与传播校验、并完成SQLite结果事务，才进入已提交集合。恢复队列跳过这些路径，机器统计仍按既有pathId和Sink/规则去重口径计算。

“同一个风险点”不等于“所有到达同一Sink的路径都完成”。两个入口的权限和传播可能不同，不能因为第一条路径完成就跳过共享Sink的其他路径。每条路径完成，风险点统计再按既有组合去重。

### 4.2 路径层：会话与宿主状态共同对齐的安全边界

首版建议仅在一个完整应用轮次结束、模型continue/finish结构已校验、该轮工具结果全部结算后建立检查点。不要在任意token、半个JSON或任意tool_execution_end处宣称可以安全继续。

每份检查点包含：

| 类别 | 建议内容 |
| --- | --- |
| 作用域与版本 | projectId/runId/pathId、snapshotId/sourceStamp/pathHash、规则/模板/项目要求摘要、模型非敏感配置摘要、工具/验证器/提示协议版本 |
| 原生对话位置 | Pi sessionId、认证过的leafId、安全会话副本的相对路径、字节长度和摘要 |
| 宿主执行状态 | 完成轮次、请求/工具次数、已读取步骤、证据指纹、证据字节、无进展次数、剩余预算、下一动作 |
| 证据索引 | 工具参数、固定文件/范围、原文摘要、受控输出引用；只记录真正读到的材料 |
| 待核查清单 | 尚未覆盖步骤、缺失的传播/防护检查及公开next；区分机械可证明的覆盖与模型自述 |
| 执行世代 | 本次executionEpoch、前驱checkpoint、检查点状态与时间 |

恢复的是公开对话、工具结果和业务状态，不是模型隐藏推理、内部KV缓存或供应商执行线程。

## 5. 证据驱动的恢复：最值得展示的部分

恢复时先由服务验证上述身份和材料，产生一份“恢复清单”。这份清单的事实字段由程序确定，不让模型根据记忆自我认证。

例如：

```text
任务共20条路径：12条已提交，1条中断，7条未开始。
中断路径：最近安全检查点为第3轮；已读取步骤0、1。
可复用：这两个步骤的固定快照原文与合法工具结果。
仍需核查：步骤2、3；先前没有完成的请求可能再次收费。
本次恢复：使用原任务材料；生成新的执行世代，保留旧尝试记录。
```

“已读取步骤”只代表取证覆盖，不能自动写成“污染传播已经成立”。模型的中间判断可以保留为待验证内容，但最终结论仍必须经过现有validateResult/validateTaint/reconcileTaint。若对话损坏或过长需要降级，也不能用一段自然语言摘要顶替原始引用。

为每次恢复保存结构化说明，并在阶段报告保留checkpoint来源、复用与重跑范围、丢弃原因和用量不确定性。这使恢复本身也能被复核，适合演示和技术文档说明。

## 6. 三种确定的恢复结果

| 条件 | 动作 | 用户看到的说明 |
| --- | --- | --- |
| 会话、安全leaf、宿主状态和版本全部一致 | 从安全检查点分支打开原生上下文，恢复宿主状态，再继续下一轮 | 从已验证检查点继续 |
| 会话不可用/不兼容，但原快照、固定配置和证据材料完整 | 新建会话，装入可核验证据与待核查清单；必要时重跑当前未提交路径 | 上下文已重建，部分模型请求需要重做 |
| 原快照/必要配置/验证器版本无法满足 | 阻止静默续跑，明确材料缺口；需新任务或显式分支 | 原任务无法按原条件恢复 |

先实施第一种与“当前路径重跑”兜底，再增强按证据清单重建上下文。选择哪种方式由校验结果决定，不能用模型的主观恢复信心百分数。

原生重开时继续使用白名单工具及资源隔离，不采用SDK默认加载用户全局工具、项目脚本或任意扩展。SessionManager.open不能接受页面传入的任意文件路径。

## 7. 工具中断与复用规则

目前audit_read_step是固定快照上的只读取证，适合安全复用。建议工具执行记录至少区分planned、running、result_saved、attached、failed/unknown。

工具结果缓存键包括snapshotId、pathHash、工具/版本、规范化参数及输出摘要，并且校验完整作用域。缓存记录证明的是“受控工具在这份快照上产生过这份输出”，不证明模型已消费或认可它。

- 安全检查点已包含完整toolCall/toolResult对：原生恢复直接保留。
- 检查点后的结果已持久保存，但尚未进入安全对话：回到上个安全边界；如模型再次发起同一合法读取，通过工具层返回已核对缓存，并重新建立合法的调用/结果关联。
- 只看到调用开始、没有可靠结果：视为未完成，可重跑只读工具，不编造成功toolResult。
- 将来若增加写文件/外部操作：默认不自动重放，必须有单独幂等键、执行收据或人工处理。

模型请求发送后崩溃，供应商可能已计算或收费；本地无法保证“恰好一次模型调用”。保证目标应是业务结果不重复提交，同时如实记录已知与不确定用量。

## 8. 停止与恢复共享执行世代

建议运行控制至少区分running、stop_requested、waiting_external、stopped、interrupted、completed。最终枚举应与已有任务状态迁移统一评审，不能直接在前端增加一个文案就算完成。

停止流程：

1. 持久化停止请求，停止领取下一路径和发送新模型请求，返回“已受理”。
2. 向在途Pi/受控工具发取消信号；若仍未退出，显示等待外部调用结束，不冒称供应商已取消。
3. 等本地操作完成结算并封存最近安全检查点，保存stopped/阶段原因，才返回“已停止”。
4. 若等待超时，逻辑隔离旧执行并标明远端结果/用量不确定；不得让它继续回写。

每次启动/恢复分配executionEpoch。工具回执、检查点与最终提交都携带世代，SQLite只接受当前有效世代；恢复后旧请求迟到，不能覆盖新结果。停止与完成并发时，以事务顺序确定“已提交”边界：停止屏障前已经提交的结果保留，未提交的路径不因停止后收到迟到结果而偷偷完成。

预算跨恢复累计，不能每次恢复清零从而无限续跑。请求发送意图、已知usage与未知usage分开；用户扩充预算是显式操作。恢复时不自动重发已提交路径。

## 9. 两种存储之间如何保持一致

Pi会话文件和SQLite不是同一个事务，不能宣称天然原子。推荐使用独立、不可继续追加的安全检查点产物：

1. 从原生完整安全分支产生应用持有的会话副本，记录leaf与有效内容；active日志继续留作诊断。
2. 写临时文件、必要的文件同步、原子rename并验证长度/摘要；遇到错误不发布检查点。
3. SQLite事务保存宿主状态、证据引用、文件摘要并将检查点置ready。
4. 启动时只接受ready且文件/身份均验证通过的检查点。孤立文件可清理；DB有记录但文件不可验时选择较早检查点或路径重跑。

Pi createBranchedSession等API对当前manager的副作用必须在DESIGN-02实测后决定调用方式，避免为导出检查点切走正在运行的会话。优先使用公开接口与受控副本，不patch SDK私有持久化方法。

SHA-256检测不一致，不提供对恶意本地数据库修改的签名证明。普通文件权限、目录/链接检查和敏感内容隔离仍需保留。会话正文包含源码，需按本地审计材料保护；API Key不入检查点，恢复时重新安全解析凭据并检查发送许可。

## 10. 配置、模型、人工复核与SSE

源码和审查材料始终取任务固定版本。不能因为当前工作目录或项目要求变化，就把旧任务悄悄升级。模型配置需要固定非敏感元数据和版本；凭据失效或目标发生变化时停止并要求明确处理。更换模型属于新分支/新尝试，必须说明与原分析的区别并重新检查发送范围。

原授权不因会话恢复而变宽；每次实际发送仍走现有beforeSend校验。恢复上下文中新增的源码类别也必须在许可范围内。重启不能自动启动付费模型请求，应先展示恢复清单，再由用户继续。

人工复核不被恢复程序重写；新机器尝试后按既有机制提示旧基线过期。原报告也保持不变，恢复后另生成报告并说明新来源。

SSE eventId仅负责补发。恢复执行产生新的尝试/会话事件流，保存恢复自哪个checkpoint的关系。界面可以关联两段过程，但不能把旧游标当作checkpoint编号，也不能因补发终态事件再次执行结果提交。

## 11. 建议实现顺序和必做实验

| 阶段 | 工作 | 通过标准 |
| --- | --- | --- |
| DESIGN-02 | 真实Pi+本机模型替身进行保存/重开/安全分支/继续；工具开始后强杀、完整工具对之后强杀 | 重开后上下文和工具序列合法；不凭存储探针推断实际续跑 |
| RUN-01 | 停止协议、等待状态、任务持久化、提交屏障 | 停止受理与停止完成可区分；旧执行不能迟到写入 |
| RUN-02基础 | SQLite任务/Pi关联、路径提交幂等、原材料恢复 | 多次重启不重复已完成路径；中断路径可明确重跑 |
| RUN-02亮点 | 安全轮次检查点、宿主状态、证据复用、恢复清单 | 当前路径可从有效检查点继续，失败可解释降级 |
| 增强 | 会话不可用时按证据重建、上下文容量策略 | 保留必要原文引用与待核查项，不能摘要冒充证据 |

故障注入至少覆盖：模型请求中断、只写toolCall、工具结果已落库但未附着、会话文件已发布但SQLite未提交、结果事务提交后SSE未送达、停止/完成竞争、恢复后旧请求迟到、半行JSONL/损坏文件、版本/配置变化、多次连续崩溃、预算耗尽。

衡量亮点应比较三种基线：整条未提交路径重跑、只恢复原始聊天、推荐的可验证恢复。指标包括完成路径重复执行数、重复提交数、源文件读取次数、恢复耗时、重复模型输入token、已知/未知费用、遗漏的必要证据和最终结论可验证率。不能预先承诺固定百分比节省，也不能因少读代码就认为审计更准确。
