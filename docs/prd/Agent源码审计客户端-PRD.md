# pi-audit-harness 产品需求文档

版本：v1.0｜日期：2026-10-16｜适用范围：首版产品

本文定义 pi-audit-harness 源码审计客户端首版的产品目标、功能范围、交互流程、技术架构、开发安排和验收标准，供产品、研发与测试实施使用。

## 1. 背景与产品定位

企业蓝队在源码审计时，需要从危险函数出发，寻找外部输入入口，逐层核对参数、返回值、字段与防护逻辑，最终整理可复核的风险证据。扫描工具能提供线索，但调用链追踪、误报排查和报告编写仍占用大量人工时间。

产品通过本地语言服务器提供代码导航，由 Agent 根据污点传播规则分析调用链。客户端使用 Pi 承载 Agent，通过扩展实现 Loop & Goal 调度，以 CLI + Skill 提供代码查询和审计能力。

**产品定位：面向企业蓝队、帮助审计人员发现并复核源码风险路径的桌面工具。** 首版以单人本地工作流服务企业审计场景，团队账号、集中权限和云端协作不属于首版范围。

产品价值以减少人工查证和证据整理时间衡量。首版输出的是静态证据支持的风险判断，不包含动态利用验证。

## 2. 产品目标与用户场景

### 2.1 产品目标

1. 缩短企业蓝队从候选风险点定位到调用路径复核的时间。
2. 自动整理外部输入、参数传播、防护逻辑和危险操作之间的源码证据。
3. 提供列表、路径图、源码与报告联动的审计工作台。
4. 支持用户选择审计模板、配置提示词和模型，保留人工复核入口。
5. 通过统一查询接口和语言配置预留多语言扩展能力。

首版效果通过固定样例和真实项目试用评估，记录人工复核耗时、有效风险数、证据不足数量及报告完整性。

### 2.2 目标用户与使用场景

| 用户 | 使用场景 | 预期结果 |
| --- | --- | --- |
| 企业蓝队审计人员 | 对新项目进行安全初审 | 发现候选风险点并确定优先复核路径 |
| 企业蓝队审计人员 | 深入核查某条风险路径 | 查看输入来源、传播映射、防护判断和源码证据 |
| 企业蓝队审计人员 | 补充业务知识或特殊审查要求 | 使用项目提示词和规则配置增强分析 |
| 企业蓝队审计人员 | 整理审计成果 | 保存人工结论并导出带图形与证据的报告 |

## 3. 产品范围与需求优先级

### 3.1 首版交付目标

用户在 Windows 安装后，可自动准备 Pi 和基础工具，配置模型，从 GitHub 或本地导入 Java/Spring 项目；选择审计能力后，系统发现候选风险点，通过 Pi 循环取证，使用 Java LSP 或基础文本查询补充调用关系，最终展示可点击源码的路径图并导出报告。

首版提供企业蓝队可试用的完整工作流，覆盖项目导入、风险点发现、循环分析、证据查看、人工复核和报告导出。

### 3.3 支持边界

首版以受支持的 Java/Spring 项目及明确配置的漏洞类型为范围。复杂反射、运行时动态分派、深层跨依赖调用、跨语言传播、任意构建系统和未支持语言均应显示未覆盖项。

以普通 Maven 项目和固定 Java/Spring 样例建立首版支持矩阵，发布材料记录经过验证的项目、JDK 和语言服务器版本。Gradle、多模块与特殊构建插件依据实测标注支持情况。

首版不接入私有 GitHub 仓库鉴权；用户已拉取的源码可通过本地目录分析。macOS、Linux 客户端、团队协作、自动修复和动态利用验证不纳入首版范围。

## 4. 用户流程与交互

### 4.1 主要使用流程

1. 启动客户端，自动检查并准备 Pi、基础工具和应用自带扩展。
2. 阅读模型配置引导，手动填写服务地址、API Key 和模型 ID，按需主动测试连接。
3. 导入 GitHub 链接或本地源码目录，预检语言、规模和构建信息，生成任务快照。
4. 选择审计模板，按需补充提示词，选择基础查询或 Java LSP。
5. 查看数据发送说明并确认模型配置，开始分析。
6. 查看风险列表、当前调查目标和活动记录，展开路径及源码证据。
7. 标注人工复核结果，导出完整或阶段报告。

用户对同一项目、模型与发送范围的确认可复用；切换到超出原授权范围的模型服务时重新确认，不要求每一轮模型调用都确认。

### 4.2 首次启动与环境准备

显示环境检查、下载、安装、启动和失败原因。Pi 在应用管理目录安装固定版本，加载应用提供的扩展与 Skills，不覆盖用户已有 Pi 环境。

基础模式不依赖 Java LSP。用户选择 LSP 后，再检查 JDT-LS 及其所需 Java 运行时，展示具体下载和索引状态；运行时版本依据锁定的语言服务器验证。

自动准备失败可重试或切换基础查询。产品不得要求用户先手工执行一套未在界面说明的终端操作才能完成标准路径。

### 4.3 项目导入

**本地目录：** 选择目录，展示支持语言、忽略目录、文件规模、可识别构建文件。固定源码快照，包括未提交修改；记录快照标识和文件内容摘要。

**GitHub：** 输入链接，解析仓库和分支/提交，下载到应用管理目录并固定 commit。优先复用可用 Git 环境；缺失时通过环境准备流程处理并显示状态。安装验收覆盖无预装 Git 的标准导入路径。

目录无权限、仓库不存在、网络失败和语言不支持分别显示原因。混合语言仓库明确列出本次分析范围与跳过部分。

### 4.4 审计配置

用户可选择或新增漏洞模板，编辑“补充审查要求”，例如重点检查某种编码方式、业务封装或输入来源。新增界面提供名称、适用语言、漏洞分类、简要说明、Markdown 审计正文和预览；支持导入 Markdown 文档、SKILL.md 或包含 SKILL.md 的 Skill 目录，也可手工指定待分析风险点。

模板以审计文档为主要编辑载体，用户无需填写 JSON 或理解底层规则格式。导入后自动提取可识别的标题和描述，允许编辑并预览后保存。Skill 仅加载知识文档，不执行其中的脚本或安装命令。新增审计知识不自动等于新增漏洞发现能力；尚未验证的自定义模板明确标识其覆盖边界。

### 4.5 工作台

| 区域 | 主要内容与操作 |
| --- | --- |
| 顶部 | 源码版本、当前阶段、模型、查询后端、用量、停止/续跑 |
| 风险列表 | 类型、位置、严重程度、分析状态、人工复核状态；筛选和排序 |
| 路径图 | Source、函数、Sink、防护节点，选择不同路径，点击节点和边查看证据 |
| 源码面板 | 文件、行号、函数体、调用位置、参数映射及证据摘要 |
| 活动区 | 当前 Goal、查询摘要、分析进度、错误及预算事件 |

首版每次重点展示一条路径及必要分支，不默认绘制整个仓库调用图。图形为必交输出，但拖拽编辑、大图自动布局和自由画布不进入首版验收。

进度显示已发现、待分析、分析中、已结束的数量和当前阶段。候选集变化时不展示不准确的全局百分比。

### 4.6 风险状态与复核

| 机器路径状态 | 含义 |
| --- | --- |
| 待分析 / 分析中 | 尚未形成路径结论 |
| 风险成立（静态证据支持） | 在声明范围和假设下，外部可控数据可到达危险参数，未发现有效阻断 |
| 路径已阻断 | 当前路径有明确的不传播或有效防护证据 |
| 证据不足 | 关键调用关系、源码、依赖或路径条件未解决 |
| 无效调用链 | 有证据表明某条调用关系不成立 |

风险点与路径分别保存状态：一条路径成立即存在风险；尚有未知或未完成路径时，不能汇总为安全。全部已分析路径被阻断时，显示“当前已分析路径未发现有效风险”，同时显示覆盖限制。

严重程度与证据充分程度分开表达，不展示未经校准的百分比置信度。人工复核保留独立状态与备注，不覆盖机器结论。

### 4.7 报告

报告包含项目版本、审计范围、模板/规则/Skill/Pi/模型版本、实际使用后端、任务结束原因、发现汇总、路径图、源码证据、防护分析、未解决问题、人工复核及修复建议。

首版使用同一报告数据生成页面和 HTML，HTML 内嵌必要图形及样式，导出后无需运行客户端也可查看；同时保留 JSON。停止或预算耗尽时可导出阶段报告，明确标识结果不完整。

报告中的源码位置绑定快照。源码、模型文本和用户备注均转义，导出文件不包含 API Key。

## 5. 漏洞审计能力的配置设计

### 5.1 配置层次

| 层次 | 作用 | 首版实现 |
| --- | --- | --- |
| 通用审计规则 | 要求可追溯证据、未知处理、结构化结果 | 应用自带并版本化 |
| 语言/框架配置 | 识别入口、符号、参数绑定与框架约定 | Java/Spring 配置；预留其他语言包 |
| 漏洞模板 | Source、Sink、相关参数、防护语义、分析指令、报告字段 | 内置三类模板，支持 Markdown / Skill 导入 |
| 项目补充提示词 | 补充业务封装、审计重点和特殊判断要求 | 文本编辑、保存为本地配置 |

提示词可以增强分析，发现范围还受规则和查询能力限制。鉴权缺失、业务逻辑漏洞等不能一律建模成 Source 到 Sink 的污点路径；后续可提供其他 Goal 类型，首版不据此宣称覆盖所有常见 Web 漏洞。

### 5.2 模板数据

模板字段包括：模板 ID、版本、名称、支持语言/框架、Source 规则、Sink 规则及危险参数位置、防护说明、审计提示词、输出要求和测试样例。

用户自定义模板保存为本地版本化文档，任务记录使用的具体版本。Markdown / Skill 内容用于审计知识和步骤，不作为可执行 Pi 扩展加载；模板内的文字不能修改工具权限或结果模式。

首版内置 SQL 注入、命令注入、路径遍历三个模板及对应正反例。新模板未经样本验证时标记“自定义/未验证”，与内置已验证能力区分。

## 6. 技术选型与组件职责

以下为首版技术方案，具体依赖版本在工程验证阶段锁定并记录。

| 模块 | 技术方案 | 职责 |
| --- | --- | --- |
| 桌面 | Electron + TypeScript | 窗口、受控 IPC、Windows 安装包；平台相关逻辑集中封装，便于后续适配 |
| 界面 | React + Vite | 配置、任务和风险工作台 |
| 图形 | React Flow 类库 | 按路径绘图；首版控制图规模 |
| 源码 | 只读源码查看组件 | 优先轻量组件，Monaco 不是首版必需依赖 |
| Agent | 固定版本 Pi，优先 RPC 接入 | 界面通过适配层管理进程及事件 |
| 调度 | 自研 Pi 扩展 | Goal、循环继续条件、预算、结构化结果提交 |
| 查询 | 统一 CLI；内置 rg + Java LSP 适配 | Skill 描述如何使用，CLI 实际执行查询 |
| 状态 | SQLite + 源码快照/产物目录 | 任务、工作项、证据、结果和风险点边界恢复 |
| 报告 | 结构化数据 + 共用 HTML 模板 | 页面、HTML 和 JSON 保持一致 |
| 打包 | 成熟 Electron 打包工具，早期验证 | 按 Windows x64 准备运行时和二进制；首版不接入签名流程 |

Pi 官方提供可扩展机制及 RPC/SDK 接入方式，本产品通过扩展实现审计工作流；具体事件和接口以锁定版本验证。参考：[Pi 仓库](https://github.com/earendil-works/pi)、[扩展文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/extensions.md)、[RPC 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/rpc.md)。

首版仅交付 Windows x64，平台相关能力集中封装。其他平台适配独立迭代，详情参考[安装包分发文档](https://www.electronjs.org/docs/latest/tutorial/application-distribution)。

### 6.1 组件关系

```text
Electron 工作台
    │ 受控 IPC
本地应用服务
    ├─ 环境准备 / 源码导入与快照 / 数据与报告
    └─ Pi 进程适配层
         └─ 审计扩展：Goal & Loop
              ├─ 审计模板与 Skills
              ├─ 状态与证据存储接口
              └─ 受控 CLI
                   ├─ 默认 rg / 源码读取
                   ├─ LSP 查询 → 按语言选择服务器
                   └─ CodeGraph 接口预留
```

调度的业务规则由审计扩展维护；应用服务负责生命周期、状态存储接口和事件分发，避免界面和扩展各自维护一套不同的任务状态。

### 6.2 CLI 与 Skill 契约

统一 CLI 提供能力查询、文本搜索、读取、符号定位、定义、引用、调用者和被调用者查询。各后端可只支持部分能力；返回值必须区分成功无命中、结果不完整、索引未就绪、超时和不支持。

返回数据包含任务/快照 ID、语言、后端、文件位置、完整符号标识、调用位置、证据来源、截断标记及错误。文本同名匹配只产生候选关系，后续需结合源码或语义查询核实。

Skill 按通用审计、漏洞模板、查询后端组织，按需加载；执行逻辑、凭据和预算控制不依赖提示词实现。

## 7. 多语言 LSP 架构与 Java 首次接入

### 7.1 多语言设计要求

语言扩展包同时描述文件识别、框架规则、入口/Sink 模式及查询适配。LSP 本身只提供代码导航等语义能力，不被当作污点分析引擎。

| 模块 | 职责 |
| --- | --- |
| 语言配置注册表 | languageId、扩展名、项目根识别、运行时要求、服务器版本与启动参数 |
| 服务器管理器 | 按项目根、语言和配置启动/复用服务器，处理启动、索引、超时与退出 |
| 能力协商 | 根据服务器实际能力选择定义、引用、实现、调用层次等请求 |
| 位置适配 | 处理文件 URI、范围和位置编码，转换到统一源码引用格式 |
| 结果适配 | 将不同服务器返回值转为统一符号、调用边及查询状态 |
| 语言规则包 | 将语言/框架语义用于 Source、Sink、传播和防护分析 |

同一仓库可包含多个语言和项目根；设计不使用“每个应用只有一个全局语言服务器”的假设。首版只实现 Java 配置及 JDT-LS 适配，其他语言显示不支持，不自动下载所有服务器。

跨语言调用关系不因注册了多个服务器就视为已解决；后续需要专门的桥接规则。

### 7.2 Java LSP 首版要求

1. 自动检测或准备语言服务器运行环境，启动固定版本 JDT-LS。
2. 识别受支持项目根，显示启动、导入、索引及错误信息。
3. 查询定义和引用，结合函数范围识别调用位置；调用层次请求在能力可用时使用。
4. 在至少一个跨文件 Java 样例上获得真实语义查询结果，并参与最终风险路径分析。
5. 索引不完整或查询失败时记录覆盖缺口，可降级为文本搜索；不直接作安全结论。
6. 常驻服务由 CLI 背后的本地管理进程复用，避免每次命令重新启动和索引。

实现时不以一次诊断通知作为整个工作区索引完成的证明，也不承诺 LSP 能完全解析动态分派和反射。参考：[LSP 规范](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)、[JDT-LS 仓库](https://github.com/eclipse-jdtls/eclipse.jdt.ls)。

## 8. Loop & Goal 工作机制

### 8.1 目标与循环

项目 Goal 固定源码范围、漏洞模板、预算与结束条件。每个候选 Sink 生成调查工作项，按需增加查找入口、确认调用目标、核实防护等子项。首版单任务串行处理，不要求多 Agent。

单轮流程：领取工作项 → 加载相关证据摘要 → 按需查询源码/LSP → 分析当前传播或防护问题 → 提交结构化证据与状态 → 校验并持久化 → 判断继续或结束。

调用关系和污点传播分别保存。污染状态不能只有参数布尔数组，至少记录来源、参数/变量/字段位置、传播类型、目标位置、路径条件及防护证据。遇到缺失源码或调用歧义时允许证据不足。

### 8.2 首版结束条件

- 所有已派发工作项已形成结论或明确未解决原因。
- 用户停止；保留已提交结果，允许生成阶段报告。
- 到达时间、模型请求数、Token、深度或分支预算；停止继续扩展并列出剩余项。
- 同一问题重复查询且没有新增证据，结束当前分支为证据不足。
- 模型/工具短暂错误有限重试；持续错误保存任务，等待用户处理。

单次会话结束不自动等于项目 Goal 完成。继续条件和预算由扩展代码检查；模型输出“已完成”仍须通过工作项与证据校验。

### 8.3 持久化与恢复

首版在风险点完成或明确中断时提交检查点。崩溃后保留已完成风险点，重跑当时尚未提交的风险点；界面说明恢复粒度及可能重复产生的模型用量。

新源码或更换审计配置创建新任务，恢复任务使用原快照和配置。精细到函数或单次模型响应的无损恢复作为后续增强。

## 9. 模型配置与 OpenRouter 使用引导

### 9.1 配置原则

模型由用户自行选择和配置。客户端不自动拉取模型目录，不自动发现免费模型，不自动推荐、选择或切换模型，也不为用户创建账号或提供公共 Key。

设置页提供服务名称、Base URL、API Key、模型 ID，以及保存、编辑、删除和测试连接操作。用户可配置受支持的模型供应商、企业网关或本地模型接口；兼容性以经过验证的接口和工具调用能力为准。

### 9.2 OpenRouter 引导教程

教程可从首次配置页和设置页打开，包含以下步骤：

1. 访问 OpenRouter 官网，自行注册或登录账号。
2. 在 OpenRouter 控制台创建 API Key，并查看账号可用额度和限制。
3. 在 OpenRouter 模型页面选择适合审计任务的模型，复制准确的模型 ID；如需免费模型，由用户在官方页面自行选择。
4. 在客户端填写服务名称、官方文档提供的 Base URL、API Key 和模型 ID。
5. 点击“测试连接”，确认接口及工具调用可用，保存配置。
6. 创建审计任务时选择已保存的配置，阅读数据发送说明并开始分析。

教程提供文本说明、填写示例和官方链接，不保存实际密钥。示例模型 ID 使用占位符，不预填某个实时模型。参考：[OpenRouter 快速开始](https://openrouter.ai/docs/quickstart)、[鉴权说明](https://openrouter.ai/docs/api_reference/authentication)、[免费变体说明](https://openrouter.ai/docs/guides/routing/model-variants/free)。

### 9.3 连接测试与配置保存

连接测试只在用户主动点击后执行，使用不含项目源码的固定样例。结果区分地址或网络错误、鉴权失败、模型不存在、额度不足、限流和工具调用不兼容，并提供处理说明。连接测试可能产生少量调用用量，按钮附近说明这一点。

保存配置不触发模型调用。Key 使用系统凭据存储，界面只显示掩码；报告和普通日志不包含凭据。更换模型由用户主动编辑或选择配置，客户端不自动替换模型。

### 9.4 源码发送与错误处理

首次向选定服务发送项目源码前，展示服务地址、模型、发送内容类别及数据政策链接，由用户确认。同一项目、服务及发送范围的授权可复用，超出范围时重新确认。OpenRouter 各提供方的数据处理政策不同，教程提供[数据政策说明](https://openrouter.ai/docs/guides/privacy/provider-logging)。

模型服务错误有限重试；遇到 429 按服务端提示和有限退避处理，额度耗尽时保存进度。用户可以修正配置或主动更换模型后继续；任务记录实际使用模型。配额与可用性参考[官方限额说明](https://openrouter.ai/docs/api_reference/limits)。

分析验收固定参考模型与调用配置，记录模型实际标识及工具调用适配结果。用户自行配置的其他模型不自动继承参考模型的质量评价。

## 10. 数据与非功能要求

### 10.1 核心数据

| 对象 | 至少保存 |
| --- | --- |
| ProjectSnapshot | 项目来源、commit/快照 ID、文件摘要、忽略范围 |
| AuditProfile | 语言/框架、模板及版本、补充提示词、模型和查询配置 |
| ScanRun / Goal | 任务状态、工作项、预算、实际用量、结束原因、检查点 |
| CandidateSink | 规则、危险参数、文件范围、源码版本 |
| CallEdge / TaintEvidence | 符号、调用位置、数据映射、来源后端、确认状态、防护与未解决项 |
| Finding / Review | 路径结论、严重程度、证据摘要、人工复核及备注 |
| Report | 导出时结果快照、生成时间、过滤条件 |

### 10.2 执行与数据边界

目标仓库内的说明、注释、AGENTS.md、Skill 文件均作为分析材料，不自动加载为可信运行指令。只加载应用管理的 Pi 扩展和 Skills。

分析默认不修改用户源码，不启动目标业务。基础查询限制在任务快照和受控缓存内，使用参数化进程调用。Pi 通用写入、编辑和不受限命令执行能力不直接开放给审计任务；CLI + Skill 可通过受控命令工具运行。

JDT-LS 项目导入可能涉及依赖解析或构建，需验证并限制项目插件/脚本执行路径，记录网络与执行行为。仅复制源码到快照并不等于隔离目标代码执行。

应用级工具限制不能宣称为操作系统级沙箱；企业上线前另行验证隔离要求。首版也须通过仓库提示词注入、越界读写和任意命令执行的指定测试。

API Key 进入系统凭据存储，日志与报告脱敏。Electron 使用受控预加载桥接和上下文隔离，源码及模型文本按不可信数据渲染。参考：[Electron 上下文隔离](https://www.electronjs.org/docs/latest/tutorial/context-isolation)。

### 10.3 性能与可观测性

记录导入、索引、规则扫描、工具查询、模型调用的耗时、重试和用量。无法获知费用时显示未知或明确标注估算。

首版性能验收基准为 1 万至 5 万行的受支持 Java 项目、100 个候选点、单路径图不超过 50 个节点。超限可选择目录缩小范围；大规模能力后续测量，不预设全仓库性能承诺。

## 11. 开发分工与实施计划

### 11.1 排期原则

以半个月形成可试用首版为目标，参考约 10 个有效工作日安排，不将其视为刚性交付日期。开发工程师承担主要编码工作，项目负责人每天约 2–4 小时参与产品、架构、关键技术与验收；具体工作量与承担方式随进展调整。

首版聚焦 Windows x64、Java LSP、Pi 扩展、可视化和报告。优先复用成熟组件，采用单任务、路径级图形、三个内置漏洞模板、HTML/JSON 报告和风险点级恢复，减少并行建设的内容。

按可运行的阶段成果判断进度：先验证关键依赖，再跑通真实路径，随后完善界面与报告，最后集中处理安装和回归。遇到难点时调整任务拆分、协作方式和预计工期，不用尚未验证的功能替代真实成果。

### 11.2 角色分工

| 负责人 | 主要职责 | 交付与协作方式 |
| --- | --- | --- |
| 项目负责人（全栈工程师） | 锁定范围；Pi 扩展和 LSP 关键验证；定义证据模式、规则及正反例；关键代码评审；Windows 验收 | 每天 2–4 小时优先投入风险最高部分；关键适配提供可运行骨架或配对支持 |
| 开发工程师（初级） | Electron/React 页面、配置表单、项目导入、任务事件展示、列表与路径图、报告模板、打包及常规测试 | 按可运行样例和明确接口拆小任务，逐日提交可演示结果 |
| 两人共同 | CLI/状态/事件契约、集成、真实项目复核、异常测试 | 每天一次集成；关键适配由项目负责人提供可运行骨架或配对完成 |

不额外假定有独立产品、测试、安全人员。样本标注与人工复核由项目负责人承担，开发工程师整理测试记录和执行回归。

- 技术验证阶段检查 Pi 扩展、Java LSP 和 Windows 安装是否跑通；有阻碍时尽早共同解决。
- 真实审计闭环完成后再扩展样本和交互，避免界面已齐全但分析链路尚未成立。
- 核心输出完成后逐步收敛新增需求，将精力转向安装、故障处理和回归。
- 任务分工可协商。项目负责人优先处理影响整体进度的接口、架构和关键适配，开发工程师按小任务完成编码并持续集成。
- 聊天、多任务并发、复杂规则编辑、复杂图探索和更多导出格式留到后续；Java LSP、Windows x64 安装包、路径图及报告保留为首版核心。
- 阶段工期变化及时更新计划；若涉及核心范围调整，再共同确认。

## 12. 测试与验收

### 12.1 验收环境与样本

至少一台 Windows x64 的真实或受支持虚拟测试环境，记录系统、CPU、内存、Pi/JDT-LS/Java 版本及网络条件。仅在开发机器启动或仅产出安装文件不算 Windows 安装验收。

建立不少于 18 个小型安全样例：三个内置模板各至少 2 个风险成立、2 个有效阻断样例，另补 6 个调用歧义、缺依赖、循环或防护不明的样例。配合一个可固定版本的真实 Java/Spring 项目，验证完整流程。

开发与验收样例分离，样例结论由项目负责人标注。先在固定参考模型上评测，再由测试人员手动配置一个可用免费模型进行兼容性验证；记录模型、模板、规则、源码和查询后端版本。首版样本较小，只形成试用基线，不据此宣称普遍准确率。

### 12.3 分析质量验收

分开测量候选 Sink 发现、调用边正确性、污点判定和证据定位，不以“任务完成”替代质量检查。

首版质量基线：验收样例中声明支持的 Sink 全部命中；简单正反例得到预期结论；关键依赖缺失、超时和调用歧义不错误判为安全；所有输出引用均可定位；真实项目至少展示一条经人工复核的风险或阻断路径。

上述基线用于首版支持范围内的小规模验证。每个样例运行三次，记录通过数、未知数和失败原因，作为验收附件；未达到基线的用例应修复或明确列入未支持范围。普遍准确率需在扩大样本集后独立评估。

### 12.4 性能和稳定性

- 参考仓库和机器在技术验证后固定；模型耗时、LSP 索引耗时与本地 UI 响应分别记录。
- 100 个候选条目和 50 节点当前路径图可用，长时间查询不阻塞界面。
- 停止请求 2 秒内得到界面确认，5 秒内停止派发新工作；外部请求取消失败时明确显示等待状态。
- 完成一次至少 1 小时连续运行和一次进程中断恢复测试，无未受控循环和已提交结果丢失。
- 外部模型可用性和额度不作为产品可控制的扫描时长承诺；固定参考样例记录耗时、请求数与 Token。

## 13. 风险管理与后续规划

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 开发经验与关键适配复杂度不匹配 | 实际工期出现波动 | 项目负责人参与关键验证与骨架，开发工程师按小任务集成；按阶段成果调整节奏 |
| Windows 测试环境不足 | 安装及运行问题发现较晚 | 尽早准备 Windows x64 环境，阶段内持续验证安装和真实运行 |
| LSP 构建与运行时差异 | 安装/索引失败、结果遗漏 | 锁定支持矩阵，显式暴露索引和降级状态 |
| 用户配置模型的能力或配额不满足任务 | 长任务中断、结果差异 | 主动连接测试、明确错误、有限重试和检查点；由用户调整模型配置 |
| 提示词扩展被误认为完整漏洞覆盖 | 用户预期失真 | 模板区分发现规则与分析增强；显示已验证范围 |
| 调用关系与污点关系混淆 | 错误风险结论 | 保存调用位置和数据映射，未知关系保持待定 |

首版之后优先根据蓝队试用结果扩大模板与 Java 构建覆盖，再逐项增加语言服务器、CodeGraph、精细恢复、私有仓库和增量分析。团队协作、集中策略与更强隔离按企业部署需求独立规划。

## 14. 发布与交付标准

首版按开源项目发布，交付 Windows x64 安装包、完整源码、锁定依赖、内置三类漏洞模板、Skills、构建说明、模型配置教程、示例报告和测试记录。

1. P0 功能完成，核心路径从安装、导入到图形与报告可完整执行。
2. Java LSP 和默认文本查询分别完成真实项目验证，故障与降级状态可观察。
3. 固定验收样例完成质量评估，结果与已知限制如实记录。
4. 无阻断安装、任务执行、证据查看和报告导出的缺陷。
5. 模型凭据、源码发送、目标代码执行边界及报告渲染通过对应测试。
6. 开源许可证与第三方依赖说明齐备，README 包含运行环境、构建步骤、使用方法和限制。

安装包采用未签名方式交付，签名与企业分发流程不作为首版发布条件。具体支持的 Windows 版本、Java/JDT-LS 版本与项目构建场景以随包兼容矩阵为准。
